# Развёртывание FIVEROX в российском контуре

Runbook от 13.11.2026. Оператор по сведениям владельца — ООО «Автопленки», ТМ FIVEROX; планируется больше 30 пользователей. Это инструкция к подготовленной версии, а не акт выполненного развёртывания, юридическое заключение или гарантия соответствия 152-ФЗ.

**Текущий статус:** Docker и Caddy на компьютере проверки отсутствуют. Образ не собирался, `docker compose up` не выполнялся, Caddy/DNS/реальный SMTP/обычная PostgreSQL не проверены. Автоматические SQL/API-проверки выполнены локально в PostgreSQL PGlite/WASM с отдельной restricted-role; они не проверяют облако, параллельные подключения, нагрузку, репликацию и восстановление.

## Что развёртывается

- `Dockerfile` — Node.js 24, только production-зависимости `pg`/`nodemailer`, приложение от непривилегированного пользователя `node`.
- `compose.yaml` — один контейнер приложения и один Caddy на одном сервере. Приложение не публикует 8080 наружу, работает с read-only filesystem и без Linux capabilities.
- `Caddyfile` — HTTPS для собственного домена и проксирование к `app:8080`. Указанный домен должен быть под контролем ООО; это не адрес GitHub Pages.
- Управляемая PostgreSQL, резервная нода, S3 и почтовый сервис **не создаются этим compose**. Их выбирают и настраивают отдельно в согласованном российском контуре.

Два узла PostgreSQL дают резервирование базы, но **не всей CRM**: один сервер приложения/Caddy остаётся точкой отказа. Для полной схемы высокой доступности нужны минимум второй экземпляр приложения и отдельный балансировщик, что в этот compose не входит. S3/загрузка фотографий и файлов договоров в этой версии не реализованы.

## 1. Подготовить аккаунт и размещение

До подключения реальных карточек подтвердить договор и ресурсы на ООО «Автопленки»: российскую локацию API/БД, место хранения резервов и логов, поручение обработки, доступ администраторов и поддержку восстановления. Отдельно согласовать технические и организационные меры, основания передачи дилерам и сроки хранения. Логотип «152-ФЗ» у провайдера не доказывает соответствие нашей CRM.

GitHub хранит исходники без рабочих данных. Закрытая CRM обслуживается российским сервером. GitHub Pages содержит публичный просмотр с выключенным API и не является рабочим backend. Не копировать дампы, реальные `.env`, секреты, журнал и клиентские вложения в репозиторий или CI artifacts.

Нужны собственный домен, сервер с поддерживаемым Docker Engine/Compose v2, управляемая PostgreSQL с приватным endpoint, доступное серверу сетевое соединение к БД, CA провайдера и SMTP с проверенным TLS. Серверный firewall открывает наружу 80/443; административный доступ ограничивается. 5432 и 8080 публично не открываются.

## 2. Секреты и конфигурация

Секреты хранить вне checkout, например в защищённом каталоге `/opt/fiverox/secrets`. Реальный `deploy/.env` имеет права 0600, принадлежит обслуживающему администратору и не попадает в Git. На выбранном сервере:

```sh
cd /opt/fiverox/platform/deploy
cp .env.example .env
chmod 600 .env
```

Заполнить `.env` через защищённый редактор/хранилище секретов. Не пересылать файл в чат и не вставлять пароль в командную строку.

| Переменная | Требование |
|---|---|
| `CRM_DOMAIN` | Реальный hostname кабинета; без `https://` и пути |
| `APP_ORIGIN` | Точно `https://` + тот же hostname; без `/` в конце |
| `TLS_EMAIL` | Согласованный служебный адрес для сертификата; учесть внешний ACME-сервис в карте потоков |
| `APP_SECRET` | Новый случайный секрет не короче 32 символов, не шаблон; не использовать секрет прежнего Google-проекта |
| `DATABASE_URL` | Приватный endpoint и **restricted runtime**-пользователь, не migration-owner |
| `DATABASE_CA_FILE` | Внутри контейнера `/run/postgres-ca.crt` |
| `POSTGRES_CA_PATH` | Абсолютный путь к проверенному CA на сервере; файл доступен UID контейнера для чтения и смонтирован read-only |
| SMTP-параметры | `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`; порт 465 либо 587 с TLS |

CA — публичный сертификат доверия, не приватный ключ. Его целостность контролируется; права чтения должны позволять контейнеру `node` прочитать файл. Не добавлять `sslmode`, `sslrootcert` и иные SSL query-параметры в `DATABASE_URL`: код использует проверенный TLS через `DATABASE_CA_FILE` и запрещает переопределение через URL.

SMTP и почтовые получатели входят в карту обработки данных. Письма содержат только код входа, не карточки и заметки. Доставка на иностранный почтовый ящик не становится автоматически внутренней российской операцией только из-за российского SMTP-отправителя. Настроить домен отправителя и требования выбранного провайдера к SPF/DKIM/DMARC.

## 3. Собрать образ и проверить конфигурацию

Контекст сборки — корень новой платформы; запускать из `deploy`. `.dockerignore` исключает локальные данные/секреты типовых имён, но не заменяет проверку содержимого checkout. Production-образ не содержит PGlite и dev fixtures.

```sh
docker compose --env-file .env -f compose.yaml config --quiet
docker compose --env-file .env -f compose.yaml build app
```

`config --quiet` проверяет конфигурацию без печати развёрнутых значений секретов. Не публиковать вывод обычного `docker compose config`, если он содержит реальные переменные. Сборка и проверка этой командой пока не выполнялись в текущей среде.

## 4. Миграция, роли и первый администратор

Сначала использовать пустую тестовую PostgreSQL в РФ. Не подключать текущую Google Таблицу и не импортировать реальные 178 карточек автоматически.

Создать отдельную migration-учётную запись и применить `server/migrations/001-platform.sql` через `src/migrate.mjs`. Для one-off контейнера передать `MIGRATION_DATABASE_URL` из защищённой среды, не записывая его в постоянный runtime `.env`. Например, при уже безопасно экспортированной переменной:

```sh
docker compose --env-file .env -f compose.yaml run --rm --no-deps -e MIGRATION_DATABASE_URL app node src/migrate.mjs
```

Создать ограниченную LOGIN-роль `fiverox_runtime` через административный процесс провайдера: `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`. Пароль задаётся в защищённом административном канале. Runtime не состоит в роли владельца схемы/таблиц. От migration-owner выполнить содержимое `server/migrations/runtime-grants.sql` в авторизованном SQL-клиенте. Постоянный `DATABASE_URL` использует именно эту роль.

На пустой таблице пользователей создать только первого администратора. `INITIAL_ADMIN_EMAIL` и `INITIAL_ADMIN_NAME` ниже — безопасно заданные оператором значения, не буквальные строки из примера:

```sh
docker compose --env-file .env -f compose.yaml run --rm --no-deps -e MIGRATION_DATABASE_URL app node src/bootstrap.mjs --email "$INITIAL_ADMIN_EMAIL" --name "$INITIAL_ADMIN_NAME"
unset MIGRATION_DATABASE_URL
```

Bootstrap не отправляет письмо и отказывается работать с непустой таблицей пользователей. Последующих людей добавляют через административный кабинет. Не запускать `seed.mjs` и не использовать `--demo` на рабочей базе. Новые production-изменения схемы оформлять отдельными нумерованными миграциями, а не считать повторное исполнение изменённого 001 механизмом обновления.

## 5. Запуск, DNS и TLS

DNS домена указывает на вход российского сервера; лишние/устаревшие AAAA-записи убраны либо обслуживаются корректно. Для автоматического HTTPS Caddy доступны входящие 80/443. Сертификат не обходится через исключение безопасности браузера.

```sh
docker compose --env-file .env -f compose.yaml up -d
docker compose --env-file .env -f compose.yaml ps
```

`GET /api/health` проверяет живой процесс и не является полноценной проверкой доступности БД, SMTP или правильности прав. Нужен отдельный контроль ошибок приложения и почтовой доставки. После запуска проверить:

- HTTPS без предупреждений, корректный сертификат, HSTS, отсутствие открытого 8080;
- `/config.js` на рабочем сервере включает только same-origin `/api` без секретов;
- без входа `/api/workspace` возвращает 401 и не содержит карточек;
- `/__dev/mail` возвращает 404; случайных demo-аккаунтов нет;
- runtime не superuser/BYPASSRLS/владелец или наследник owner: startup должен отказать при таком подключении;
- `.env`, CA/private keys, дампы и журналы не доступны по HTTP;
- логи не содержат кодов, cookies, паролей, карточек и полного request body. Проверить это также для reverse proxy и выбранного внешнего мониторинга.

Ротация Docker-логов в compose ограничена размером `10m × 3` на контейнер; это не юридически определённый срок хранения и не резервная копия бизнес-журнала.

## 6. Приёмка SMTP и двух дилеров

Для проверок использовать отдельные согласованные тестовые адреса. Реальные менеджеры и право доступа добавляются только по решению администратора.

1. Владелец запрашивает код. Проверить реальную доставку, срок, один успешный вход и отказ повторного использования. SMTP-ошибка должна быть понятна пользователю; код не сохраняется в отчёте.
2. Добавить две разные дилерские организации А/Б и отдельных сотрудников. Успешный вход без назначений не открывает общую базу.
3. Создать отмеченные тестовые карточки и непустые синтетические контакты. До принятия передачи видны только разрешённое резюме, название и город; полный контекст скрыт.
4. Передать карточку А с контактом только после явного выбора, принять под А, внести этап/заметку/контакт/продажу. Независимо перечитать БД и журнал: actor, время, точные до/после и отсутствие дубля при повторе operation ID.
5. Под Б проверить список, поиск, прямой ID, дочерний POST/PATCH и аналитику: чужие данные/итоги не раскрываются. Подмена роли, actor/dealer/client/assignment не помогает.
6. Переназначить А→Б без контактов. Доступ А прекращается; Б не получает старые заметки, договор, историю, продажи и контакты автоматически. Отзыв проверяется также из уже открытого старого черновика.
7. Отозвать и повторно назначить тому же сотруднику новую передачу. Старый operation ID не должен вернуть private receipt прошлого назначения.
8. На обычном PostgreSQL проверить двумя одновременными соединениями конкурирующие правки ребёнка/карточки, принятие/отзыв и ошибки аудита. Старые версии дают конфликт, не теряется последняя правка, одно активное назначение сохраняется. Локальная последовательная PGlite-проверка это не заменяет.
9. Выйти, обновить страницу: cookie/серверная сессия не дают автоматического возврата. Отключить пользователя и проверить все последующие операции.

Сохранять статусы `passed/failed/not_tested`, выпуск кода, роль и безопасное доказательство. Одной суммы зелёных локальных тестов для production-приёмки недостаточно.

## 7. Резервное восстановление и перенос живой базы

Проверить в договоре и консоли провайдера российское место резервов, срок/частоту, PITR и действия при отказе. Два узла БД не заменяют резервные копии. Штатные копии управляемой PostgreSQL Selectel на момент исследования дают восстановление за последние 7 дней; фактические условия выбранного ресурса сверяются перед заказом.

В отдельной закрытой БД восстановить резерв на согласованное время. Проверить не только сообщение «восстановлено», но и ID/числа карточек, рабочие значения, назначения, историю и аудит. После восстановления вернуть runtime grants/RLS/проверенные параметры подключения; отозвать скопированные сессии и незавершённые коды, проверить секреты и DNS. Тестовый восстановленный контур не должен отправлять письма реальным пользователям; доступ и исходящая почта ограничиваются до проверки.

Если нужен отдельный экспорт, `pg_dump`/`pg_restore` выполняются обслуживающим администратором с защищённым connection service/секретами, шифрованием и российским хранилищем. Дамп не загружается в GitHub, Google Drive или зарубежный сервис диагностики. Доступность S3 и резервирование файлов проверяются отдельно после реализации загрузки файлов.

Только после этих проверок выполнять контролируемый импорт исходных 178 карточек: stable ID, ручные восемь полей, контакты и исходные авторы/даты сохраняются; текст «ответственный» не превращается в разрешение. Финальный перенос предусматривает окно без параллельных правок, отчёт сверки и однозначный рабочий источник. Прежние сайты/Google Таблицы/Apps Script не удаляются этой инструкцией; их дальнейшее хранение, отзыв доступа и очистка зарубежных копий согласуются отдельно.

## Откат и эксплуатация

Перед обновлением фиксировать commit/образ и совместимую схему. Откат приложения к старому образу возможен только при совместимой БД; откат миграции или данных требует отдельного плана. Не возвращать незаметно старую зарубежную базу в качестве production-источника ради восстановления доступности.

Нужны ответственный за обновления ОС/приложения, мониторинг сертификатов/баланса/БД/SMTP, оповещения, проверка восстановления и правила очистки истёкших auth-записей. Провайдер обслуживает управляемую БД, но не всю логику CRM. Минимальную конфигурацию 30+ пользователей подтверждают нагрузочным испытанием, а не количеством зарегистрированных аккаунтов.
