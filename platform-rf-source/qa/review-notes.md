## Найдено и исправлено авторами

- Logout терял CSRF после локальной очистки session; frontend теперь явно передаёт captured CSRF при запросе выхода. Production/browser-проверка cookie ещё нужна.
- Новые `AUTH_REQUIRED` не совпадали со старыми `CRM_AUTH_REQUIRED`; frontend теперь нормализует ошибки и очищает сессию централизованно, в том числе в прямых admin/transfer вызовах.
- Создание карточки передавало восемь рабочих полей в несовместимой форме; frontend теперь передаёт `fields[8]`, backend должен сохранять их без потери.
- Недоступный getter `localStorage` мог обрушить весь рынок; getter перенесён в try/catch, независимый regression test прошёл.
- Строка прайса не ссылалась на свой `p.url`; frontend добавил проверяемую ссылку источника цены.
- «Добавить точку» создавал заявку; frontend добавил отдельный `kind=customer`, backend-author подтвердил отдельную квалификацию/профиль. Эти новые API ещё требуют integration проверки.
- В ранней валидации integer-параметр создавал недопустимый decimal regex, а некорректная дата падала как RangeError; backend исправил. Независимая проверка: обычное действие валидируется, некорректная дата даёт 400.
- Неправильный тип `links` первоначально давал TypeError; передан backend-author для type guard.

## Важные точки backend, переданные автору

- У pending-получателя не было доступа к строке клиента для `FOR UPDATE`, а setting перехода не использовался политиками. Автор добавил узкую server-only transition scope; требуется non-owner RLS тест.
- Переназначение A→B не могло отозвать старую строку при прежнем RLS. Автор скорректировал transition policy. Тест должен реально работать как restricted role, иначе superuser скрывает дефект.
- Имя/город pending-предложения читались через недоступный клиентский JOIN. Автор добавил отдельный snapshot безопасной проекции.
- Глобальный `profileData.contractReference` не должен автоматически раскрывать договор прежнего дилера новому. Передано автору для whitelist либо явно утверждённой проекции и regression.

## Дополнительные независимые проверки

`qa/reviewer-backend-extra.test.mjs` проверяет явное сохранение восьми полей, непустые синтетические контакты (`shareContacts=false/true`), смену получателя, raw SQL SELECT restricted-role, просроченное предложение со старым активным назначением, запрет реальных адресов в dev-mailer, fail-closed production SMTP и запрет production mail sink.

Первые восемь сценариев прошли. Девятый добавлен после выявления scope replay: **до исправления 8 passed / 1 failed**.

Открытые на момент этого обновления вопросы переданы backend-author:

1. **Scope binding идемпотентности (воспроизведено).** После revoke и нового назначения тому же менеджеру старый `saveClient` operation ID возвращает старый private receipt с данными прежнего назначения. Текущая авторизация нового назначения недостаточна; receipt должен быть привязан к конкретному dealer/assignment scope. Проверка `A same-user reassignment cannot replay the previous assignment private card receipt` пока падает `Missing expected rejection`.
2. **Конкурентное изменение дочерней записи (code finding).** Ранний `saveItem` читал `old/version` до блокировки клиента; после ожидания клиентского lock мог сравнить устаревшую копию и затереть чужую правку. Требуется читать запись после общей блокировки и проверять версию в UPDATE. PGlite сериализует транзакции и не доказывает реальную двухсоединительную гонку.

Не считать эти два пункта исправленными без повторной проверки исходников и теста replay. История раннего обнаружения сохраняется; окончательный результат уточняется ниже после исправления.

### Финальный повтор после исправлений

Оба пункта исправлены backend-author и повторно проверены независимо:

- Идемпотентный digest для менеджера включает роль, дилера и ID текущего назначения; повтор прежней операции в новом назначении отвергается. Ранее падавший blackbox regression теперь проходит.
- `saveItem` сначала блокирует клиента, затем перечитывает дочернюю запись `FOR UPDATE`. Обновление содержит `WHERE id = … AND version = … RETURNING id` с конфликтом при отсутствии строки. Порядок и условие проверены по коду; реальная конкурентная проверка обычного PostgreSQL остаётся `not_tested`.
- Контракт договора в `profileData` исключён из manager DTO, покрыт авторским тестом переназначения.

Итоговая независимая команда: `node --test server/test/integration.test.mjs qa/reviewer-backend-extra.test.mjs` из корня новой платформы. **35 тестов, 35 passed, 0 failed.** Дополнительно независимые frontend public/model/privacy проверки — **7/7**. Это не 42 production-сценария: все автоматические проверки локальные.

Критических неисправленных дефектов в рассмотренном коде на момент этого повтора не осталось. Browser E2E и облачная production-приёмка выполняются root отдельно; квалификация, API/форма, logout cookie и два пользователя должны быть наблюдаемы в браузере до утверждения результата.

## Что нельзя считать выполненным без root-приёмки

Файлы/фото не подключены: интерфейс честно описывает эту границу. Production SMTP, российское размещение, полное восстановление, нагрузка 30+ людей, два независимых HTTP-пользователя, actual PostgreSQL pool/concurrency и новая опубликованная CRM этой статической проверкой не подтверждаются. PGlite проверяет PostgreSQL-семантику локально, но не реальную сетевую эксплуатацию и отказоустойчивость.
