# FIVEROX: сервер новой платформы

Это реализованный локально HTTP API с PostgreSQL и email-кодом, а не подключённая российская production CRM. Все штатные демонстрационные записи вымышлены; Google Sheets и реальные пользователи автоматически не импортируются. Нет утверждения о выполнении всех юридических требований или нагрузке 30+ пользователей.

## Локальная проверка

Нужен Node.js 24 и pnpm. `pnpm install --frozen-lockfile --ignore-scripts`, затем:

```sh
NODE_ENV=test node --test test/integration.test.mjs
NODE_ENV=development DATABASE_ENGINE=pglite node src/index.mjs --demo
```

В тестовой среде PostgreSQL работает через PGlite/WASM. Бизнес-транзакции выполняются как отдельная роль `fiverox_runtime` без ownership/BYPASSRLS, с включёнными RLS-политиками. Это проверяет действительный SQL PostgreSQL и изоляцию, но **не** параллельные подключения обычного PostgreSQL, репликацию, отказоустойчивость, резервное восстановление или пригодность облачного контура для 152-ФЗ.

Открыть `http://127.0.0.1:8080/`. Синтетические аккаунты: `admin@example.test`, `coordinator@example.test`, `dealer.a@example.test`, `dealer.b@example.test`. Они подтверждают свой адрес кодом, который создаётся случайно при каждом запросе. Код находится в локальном почтовом sink `http://127.0.0.1:8080/__dev/mail`. Он не печатается в лог и не зашит в UI. Sink доступен только с loopback и отсутствует в production. Письма на реальные адреса в dev-sink запрещены.

`DATA_DIR` сохраняет локальную PGlite. Режим `--demo` запрещён при `NODE_ENV=production`. Для тестирования HTTP локальная среда должна разрешать bind loopback-сокета.

## Production в РФ

1. Выбрать российское размещение API, PostgreSQL, файлов/логов/резервов и оформить договоры на ООО «Автопленки». Создание аккаунтов и оплата этим кодом не выполняются.
2. Создать закрытую PostgreSQL и отдельную migration-учётную запись. Применить `node src/migrate.mjs` с `MIGRATION_DATABASE_URL` и проверенным TLS/CA.
3. Создать отдельную LOGIN-роль `fiverox_runtime`: `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`; задавать пароль безопасно, не включать его в SQL-файл, командную строку, Git или отчёт. Runtime не должен быть членом migration-owner-роли.
4. От migration-owner выполнить `migrations/runtime-grants.sql`. Runtime разрешены необходимые запросы, но нет UPDATE/DELETE журнала и квитанций операций.
5. На пустой users-таблице выполнить `node src/bootstrap.mjs --email ВЛАДЕЛЕЦ --name ИМЯ` с migration-учётной записью. Этот шаг создаёт одного администратора и не отправляет письмо. Дальнейшие пользователи создаются через административный API; открытой регистрации с доступом ко всей базе нет.
6. Передать серверу `DATABASE_URL` именно runtime-учётной записи, `APP_SECRET` (случайный секрет >=32 символов), HTTPS `APP_ORIGIN`, SMTP-параметры и `DATABASE_CA_FILE`, если CA провайдера отсутствует в системном trust store. В production TLS PostgreSQL проверяет сертификат. URL с `sslmode`/SSL-параметрами не принимается, чтобы они не переопределили CA и проверку.
7. Настроить HTTPS reverse proxy, `PUBLIC_DIR` с новой версией сайта, ограничить сеть БД только приложением. Запустить `NODE_ENV=production node src/index.mjs`.
8. Проверить реальную доставку кодов, роли двух дилеров, отрицательные запросы по чужим ID, отзыв прав, журнал, параллельные транзакции и восстановление из резервов. После этого проводить контролируемый импорт, сохранив исходные ID/ручные поля/авторов и определив судьбу прежних зарубежных копий.

Сервер откажется стартовать с production PGlite, коротким/шаблонным секретом, отсутствующим HTTPS origin или SMTP-конфигурацией. Production runtime не может быть superuser, BYPASSRLS, владельцем/наследником владельца таблиц или схемы. SMTP на 465/587 использует проверенный TLS; отключения проверки сертификатов нет.

## Реальные права и сохранение

- Admin/coordinator видят общую базу. `dealer_manager` получает только карточки своего активного назначения и своей дилерской организации. Чужие дочерние записи не попадают в поиск/канбан/аналитику, поскольку workspace сразу ограничивается сервером и RLS.
- Pending-предложение содержит снимок названия компании/города и одобренное резюме, без полной карточки. Принимать может только назначенный получатель. Его принятие атомарно отзывает предыдущее active-назначение.
- Новое назначение начинает новый рабочий контекст. Старые заметки, сроки, оценки, контакты истории и продажи прежнего назначения не передаются автоматически. Телефоны/каналы передаются только после явного `shareContacts` от staff. `profileData.contractReference` остаётся staff-only.
- Все записи менеджера, отзыв и переназначение блокируют одну строку клиента и повторно проверяют доступ внутри транзакции. Проверка выполняется до возврата идемпотентного повтора — отзыв не обходится старым operation ID.
- RLS-проекция pending-статуса и разрешённого принятия использует серверный транзакционный `fiverox.transfer_client`. Он выставляется только после проверки точного получателя; браузер не получает SQL или право устанавливать контекст.
- Изменение, аудит и квитанция операции — одна транзакция. При сбое аудита откатываются данные. Version предотвращает затирку чужой правки; operation ID защищает повтор команды от дублей. Дилерская квитанция привязана к роли, дилерской организации и конкретному назначению: повторное назначение тому же человеку не раскрывает старый ответ/контакты/историю.
- Автор/время журнала задаются сервером. Runtime не может переписать события через API или SQL GRANT. Администратор БД всё ещё обладает инфраструктурными полномочиями; журнал не называется математически неизменяемым.
- Приглашение в этой версии — созданный администратором допуск на адрес с ограниченным сроком первого входа. Автоматическое отдельное письмо-приглашение пока не отправляется; пользователь запрашивает обычный OTP на форме входа. SMTP доставку в production необходимо проверить отдельно.

## Границы версии

Реализованы отдельные заявки/постоянные точки (`kind`), квалификация без смены stable ID, редактируемый профиль, исходные восемь рабочих полей, действия/визиты/тесты/оборудование, продажи, передачи, административное создание пользователей/дилеров, блокировка сессий, журнал. Договор в профиле пока реквизит, не загруженный файл. S3 и загрузка фото/документов не реализованы — UI не должен показывать их как готовые.

Миграция содержит первую схему; изменения production-схемы впоследствии должны оформляться новыми нумерованными миграциями, а не повторной правкой 001. Ограничение частоты запросов и попытки кодов сохраняются в БД. Нужны согласованные политика хранения/план очистки истёкших auth-записей, мониторинг, антивирусная проверка будущих файлов, независимый аудит и эксплуатационная приёмка.

Контракт маршрутов — `api-contract.md`; health `GET /healthz` или `/api/health` возвращает только `{status:"ok"}`. `GET /config.js` на сервере включает same-origin API без секретов; GitHub preview может иметь API выключенным. `APP_ORIGIN` задаётся без завершающего `/`. Сервер не доверяет роли/actor/dealer из тела запроса; cookie + CSRF + Origin проверяются на HTTP.
