# Контракт данных и сохранения

## Схема

Начни с чтения вкладок, заголовков, размеров, формул, validation и защит. Зафиксируй mapping полей явно; колонка J прежнего проекта не является универсальным адресом.

| Сущность | Минимальные поля | Инвариант |
| --- | --- | --- |
| Карточка | lead_id, название, город/адрес, услуги, контакты, URL источников | ID стабилен, уникален и хранится текстом |
| Рабочие поля | этап, ответственный, следующий контакт/шаг, последний контакт, заметка, оценка сделки, причина отказа | Запись затрагивает только согласованные поля |
| Контакт | event_id, lead_id, время, тип, результат, actor | Добавление однократно для client operation ID |
| Аудит | event_id/operation_id, время с зоной, actor, действие, lead_id, changes[] | changes содержит имя поля и значения before/after |
| Очередь | ближайшие и просроченные контакты | Явно определены закрытые этапы и правила дат |

Пример FIVEROX включает 9 этапов и 5 типов контакта в [контракте](../assets/crm-contract.example.json). Не добавляй эти этапы в другой бизнес автоматически.

Разделяй историю общения и аудит изменения полей. Показывай автора контакта там, где он нужен менеджеру; наличие автора только в отдельном журнале не равно его отображению в истории. Исследовательские цены и локальные расчёты не превращаются автоматически в реальные сделки/выручку.

## Серверная запись

1. Проверь вход, роль и область разрешённых карточек. Получи actor с сервера. Проверь payload по явному контракту, число полей и допустимые значения.
2. Найди ровно одну карточку по `lead_id`. Отсутствие и дубликат — ошибка, а не повод молча писать в первую строку.
3. Под блокировкой скрипта перечитай исходную версию/рабочие поля и сравни с клиентской версией. Конфликт не должен затирать чужую правку.
4. Валидируй длину текста, календарные даты с зоной, диапазон и точность суммы, этап и тип контакта. Записывай пользовательский текст как строку, сохраняя формулы только там, где они уже разрешены. Не позволяй заметке `=...` стать формулой.
5. Подготовь точечное обновление и audit diff. Сохрани неизменённые формулы, форматирование и validation. При пустом diff не создавай ложное событие.
6. В пределах одного файла отправь рабочую правку и добавление аудита одним `spreadsheets.batchUpdate`. При ошибке журнала сохранение должно завершиться ошибкой, без частичной рабочей правки. Это гарантирует совместное применение запросов API, но не изоляцию от ручных редакторов Sheets.
7. Верни подтверждённое состояние/версию; UI показывает успешное сохранение после ответа и делает нужное повторное чтение.

`ScriptLock` координирует вызовы того же скрипта. Он не блокирует человека в Google Sheets, другой проект или внешнюю интеграцию. Для строгой конкурентной работы и аудита запрети обходной канал в рамках выбранной модели либо выбери транзакционное хранилище.

## Канбан и потерянный ответ

Перемещение передаёт ID, предыдущий этап, новый этап и при необходимости версию/operation ID. Сервер проверяет актуальный этап. При конфликте UI возвращает авторитетное состояние и объясняет результат. На телефоне доступен выбор этапа в форме.

Повторный запрос записи контакта после потерянного ответа может создать дубликат. Передавай с клиента уникальный operation ID, проверяй на сервере уже применённый результат под блокировкой, фиксируй его вместе с изменением и возвращай тот же результат при повторе. UUID, созданный только при append журнала, сам по себе не обеспечивает идемпотентность. Не добавляй слепой retry к операциям без такой защиты.

## Аудит и масштаб

Редактор рабочего файла может изменить ячейки и журнал напрямую. Журнал приложения документирует действия через приложение. Полный аудит ручных изменений, защита от подделки и восстановление требуют отдельного решения. Не обещай, что `onEdit` сам решает полную идентификацию всех авторов и всех типов записи.

Ограничивай чтение диапазонами, используй batch чтение/запись и измеряй задержки на реальном размере. Не придумывай предел «N пользователей», проверенный по одной карточке. Рост истории, сканирование всех строк, квоты, задержки и конфликтующие каналы — основания оценить переход на БД. Объём прошлого кейса не является нагрузочным тестом нового проекта.
