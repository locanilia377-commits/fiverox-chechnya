# Развёртывание и диагностика

## Паспорт выпуска

Используй [пример manifest](../assets/release-manifest.example.json) как структуру, а не доказательство проверки. Указывай фактический frontend commit/hash, backend deployment ID/version, execute-as/access, схему, дату, браузер, роль тестового пользователя и результаты. Legacy-маршруты отмечай отдельно. Не накапливай старые проверки без привязки к версии.

Для существующего проекта различай рабочие исходники, старые копии, сгенерированный HTML и реально опубликованные файлы. Сверь целевой deployment и сборщик. Новый файл OAuth в локальной папке не доказывает его включение в серверный выпуск.

## Apps Script и статический кабинет

В кейсе использовалась цепочка GitHub Pages → POST API Apps Script → закрытая Google Таблица. Кабинет не отправляет браузер менеджера на `/exec` и не использует его Google cookies. Это устраняет зависимость клиентского маршрута от Google multi-login; доступность сети и провайдера всё равно проверяется отдельно.

Apps Script multi-login официально не поддерживается. Инкогнито/один аккаунт помогает диагностике, но не является удобным командным продуктом. Не пытайся бесконечно исправлять `/u/3/`, `authuser` и accounts-wrapper. При повторяющемся сбое выбранного продукта меняй маршрут входа после конкретной проверки альтернативы.

В прежнем RPC использован `POST`, `Content-Type: text/plain;charset=UTF-8`, JSON `{method,args}`, `credentials: omit`, явный серверный allowlist методов, ограничения размера/аргументов, ответы `{ok,result}`/`{ok:false,error}`. Это проверенная форма конкретного проекта. Не считай MIME или CORS границей авторизации. Каждый закрытый метод должен проверять токен и роль.

ContentService перенаправляет ответ на googleusercontent. Проверяй фактическую цепочку редиректов и CORS в production браузере; не обещай общую поддержку произвольного заголовка, preflight или proxy без теста. Не обходи ограничения с помощью публичного JSONP для закрытых данных или токенов в URL.

## Порядок выпуска

1. Подготовь точечные изменения, локальный build и необходимые проверки. Сохрани текущие версии/route для отката.
2. Проверь нужные Google Services. Для `Sheets.Spreadsheets.batchUpdate` нужен advanced service **Google Sheets API v4**, идентификатор `Sheets`. Добавление AdSense или другого сервиса не подходит. Для default Cloud project и standard project настройка API может отличаться — проверь официальную документацию.
3. Выполни setup как владелец и проверь необходимые scopes. Если требуется личный consent пользователя, открой фактический экран и передай точную ссылку. Не называй «следующий экран» и кнопку, пока они не наблюдались. Не проси повторно уже выданный consent без причины.
4. Опубликуй/обнови нужную Apps Script версию с выбранным execute-as/access. Сохранение в редакторе не обновляет versioned `/exec` автоматически. `/dev` не является общедоступным production endpoint.
5. Проверь нового пользователя, backend и сохранение на тестовом маршруте. Для production-only зависимости запиши ограниченный результат и не заявляй готовность до финальной проверки.
6. Опубликуй подготовленный frontend и дождись завершения Pages deployment. Проверь анонимный HTTP и реальный browser маршрут из основной кнопки, совпадение опубликованной сборки, мобильный экран и отсутствие приватного payload до входа.
7. Выполни финальный сквозной тест текущей кнопки и при сбое верни подготовленный прежний route либо явно покажи недоступность. Обнови таблицу ссылкой и паспорт выпуска только по фактическим результатам.

## Когда код не приходит

Сначала найди точный email и время одной попытки, не проси сам код. Проверь последовательно:

| Слой | Доказательство | Следующее действие |
| --- | --- | --- |
| Форма/сеть | Запрос ушёл с опубликованного кабинета на нужный deployment | Исправить кнопку, неверный endpoint или transport |
| Разрешение | Точный адрес допущен именно в закрытом CRM-файле/реестре | Владелец выдаёт требуемую роль; не расширять доступ автоматически |
| Конфигурация | Вход включён, owner setup выполнен, секрет есть | Выполнить setup/consent в нужном проекте |
| Лимит | Причина throttled либо реальная квота отправителя | Показать корректное ожидание, не слать цикл повторов |
| Транспорт | MailApp/provider принял отправку либо вернул ошибку | Исправить отправку; submission не считать доставкой |
| Доставка | Письмо реально найдено получателем, включая spam | Зафиксировать время, затем проверить вход |
| Проверка | Код того же браузера, свежий, неиспользованный | Новый запрос после истечения/исчерпания попыток |
| Сессия/доступ | Новый token принят, актуальные права проверены | Проверить приватное чтение и сохранение |

Причины должны быть доступны администратору через безопасную корреляцию без секретов. Если интерфейс Executions не показывает Cloud logs, это отсутствие наблюдения, а не доказательство отсутствия ошибки. Добавляй ограниченную приватную диагностику вместо вывода кода в logs. Общий successful HTTP или completed execution ничего не говорят о доставке конкретному адресату.

После двух одинаковых воспроизведений не перебирать случайные URLs/настройки. Выдвинь проверяемую гипотезу и добудь различающее доказательство. При невозможности проверить конкретный шаг сообщи точную границу, сохрани работающую часть, не называй весь выпуск готовым.

## Эксплуатация

Фиксируй latency/error rate API, число конфликтов и отправок/отказов, оставшуюся квоту, размер/рост таблиц и истории. Не записывай содержимое заметок или токены в диагностические логи. Политика хранения/резервирования и восстановление проверяются отдельно; наличие файла на Drive не означает проверенный backup. Возврат frontend commit и backend версии должен сохранять совместимость схемы.
